# 聊天室协议标准（v0）

本文是**客户端与服务端之间的通信契约**：传输方式、消息格式、字段规则、边界行为。
实现代码：`shared/zodSchemas.ts`（入站校验配方）、`server/src/rooms/MyRoom.ts`（服务端）、
`server/src/rooms/schema/MyRoomState.ts`（同步状态）、`client/src/App.svelte`（客户端）。

> **不会两边写歪**：契约里能共享的部分（zod 配方与长度常量）只有一份，放在 workspace 包
> `@colyseus-chat/shared` 里，前后端各自 import。改动它之后**必须两端一起重新构建**。

## 2. 传输层

协议建立在 Colyseus 0.18 之上，连接分两步：

### 2.1 匹配（HTTP）

```
POST /matchmake/joinOrCreate/my_room
→ 200 { "roomId": "...", "sessionId": "...", "processId": "..." }   # 座位预约（seat reservation）
```

- 房间不存在就创建，存在且未满就加入。
- 返回的 `sessionId` 是**本次连接的会话 ID**，也是后续聊天消息里的发送者标识。

### 2.2 建立 WebSocket

```
GET /<processId>/<roomId>?sessionId=<sessionId>     Upgrade: websocket
→ 101 Switching Protocols
```

- 服务端在升级握手时会校验这次连接是否对应一个**未过期、未被消费**的座位预约
  （`Room.hasReservedSeat`）。校验不通过会立刻关闭连接，客户端表现为
  `MatchMakeError: seat reservation expired.`。**注意：此时 WebSocket 已经升级成功（101），
  错误发生在升级之后**，排查时不要被 101 误导。
- 升级完成后，双方按 Colyseus 的二进制协议通信：
  - **状态同步**：加入时收到一次全量状态，之后每个 patch tick 收到增量（本协议的消息记录走这条路）；
  - **消息**：`ROOM_DATA` 帧，帧内是「消息类型 + msgpack 编码的载荷」。

### 2.3 关闭

正常离开时服务端日志会记录 `left!`，观测到的关闭码有 `1001`（客户端主动离开）和 `4001`（浏览器关闭）。
框架在「校验被拒」这类路径上会用 `4002`（`CloseCode.WITH_ERROR`）——本协议**刻意不走这条路**
（见 §4 的校验策略），业务校验失败不会断连。

## 3. 房间契约

| 项       | 值        | 说明                                                           |
| -------- | --------- | -------------------------------------------------------------- |
| 房间名   | `my_room` | 注册于 `server/src/app.config.ts`；客户端 `ROOM_NAME` 必须一致 |
| 最大人数 | `4`       | `MyRoom.maxClients`；满了之后 `joinOrCreate` 会新建房间或失败  |
| 同名房间 | 不区分    | 所有连接进入同一个房间实例（本示例没有分房间逻辑）             |

### 3.1 加入参数（客户端 → 服务端）

客户端调用 `joinOrCreate("my_room", options)`，`options` 由 `JoinOptionsSchema` 校验：

| 字段   | 类型     | 必填 | 规则                                                |
| ------ | -------- | ---- | --------------------------------------------------- |
| `name` | `string` | 否   | 先 `trim()`，长度 1~20（`MAX_NAME_LENGTH`）；可省略 |

- 昵称**只在加入时确定一次**，会话期间不变，也没有改名消息。
- `name` 缺失、为空、超长或非字符串 → **不拒绝加入**，昵称退化为 `sessionId`，保证界面上总有可显示的名字。

### 3.2 发送消息（客户端 → 服务端）

| 项          | 值                                                                                |
| ----------- | --------------------------------------------------------------------------------- |
| 消息类型    | `chat`（`room.send("chat", payload)`）                                            |
| 载荷        | `{ text: string }`，由 `ChatPayloadSchema` 校验                                   |
| `text` 规则 | 先 `trim()`，长度 1~500（`MAX_MESSAGE_LENGTH`）；**只去首尾空白，不合并中间空格** |

### 3.3 接收消息（服务端 → 客户端）

本协议**没有把聊天记录做成事件**，而是放在房间的同步状态里：

```
room.state.messages : ChatMessage[]        // ArraySchema，按追加顺序排列
```

| 字段        | 类型     | 含义                                                          |
| ----------- | -------- | ------------------------------------------------------------- |
| `sessionId` | `string` | 发送者会话 ID；客户端用它判断哪条是自己发的（自己的靠右显示） |
| `name`      | `string` | 发送者昵称（加入时确定，见 §3.1）                             |
| `text`      | `string` | 消息正文（已 `trim`）                                         |
| `timestamp` | `number` | **服务器**时间戳，毫秒级 Unix 时间；客户端只用它显示「时:分」 |

**为什么用状态而不是事件**：写状态天然等于广播（框架自动同步给房间里所有人），
而且后加入的人会在初始全量状态里**一次性拿到历史**，不需要额外的「拉历史」请求，
也不会出现「事件 + 历史」两条投递路径不一致的问题。

### 3.4 成员列表

同一份状态里还有当前房间的成员：

```
room.state.members : Map<sessionId, name>     // MapSchema<string>
```

| 项     | 说明                                                                        |
| ------ | --------------------------------------------------------------------------- |
| key    | `sessionId`                                                                 |
| value  | 昵称（加入时确定，见 §3.1）                                                 |
| 顺序   | 遍历顺序 = 加入顺序                                                         |
| 更新   | 有人加入 / 离开（含掉线）时增量同步，客户端用 `onAdd` / `onRemove` 监听即可 |
| 初始值 | 后加入的人会在初始全量状态里拿到**完整的当前成员列表**                      |

用 map 而不是数组，是为了有人离开时能按 `sessionId` 直接删除，不用维护下标。

### 3.5 历史语义

- 房间只保留**最近 50 条**（`MAX_HISTORY_MESSAGES`），超出后从最旧的开始丢弃（FIFO）。
- 历史保存在**房间内存**里：房间销毁（所有人都离开后自动 dispose）后，记录随之消失。
  刷新页面、重新加入看到的是「当前房间实例」的历史，而不是永久记录。
- 新加入者收到的是**当前那一刻**的全量数组；之后按增量同步追加。

## 4. 校验策略（重要）

服务端对**所有**入站数据都独立校验，永不信任客户端。但两侧的校验**目的不同**：

| 侧     | 做法                                                          | 失败时的行为                                                  |
| ------ | ------------------------------------------------------------- | ------------------------------------------------------------- |
| 客户端 | `ChatPayloadSchema.safeParse` / `JoinOptionsSchema.safeParse` | 本地提示错误（「消息不能为空，且不超过 500 字」），**不发包** |
| 服务端 | 同样用共享配方 `safeParse`                                    | **丢弃这条消息** + 打一条 `console.warn`，连接保持不变        |

服务端**刻意没有使用** Colyseus 自带的 `validate()` 包装器：它在校验失败时会
`client.leave(CloseCode.WITH_ERROR)`（见 `@colyseus/core` 的 `onData`），也就是**把客户端踢下线**——
对聊天室来说太重了（一句话超长就掉线显然不合理），所以改成 `safeParse` + 丢弃 + 日志。

## 5. 边界行为一览

| 场景                         | 行为                                                                                 |
| ---------------------------- | ------------------------------------------------------------------------------------ |
| `text` 为空白字符串 `"   "`  | trim 后为空 → 服务端丢弃，不写入历史                                                 |
| `text` 不是字符串（如 `42`） | 校验失败 → 丢弃（服务端不会抛异常）                                                  |
| `text` 超过 500 字           | 校验失败 → **整条丢弃**（不是截断）；客户端输入框有同样的 500 字上限，正常用户碰不到 |
| 载荷缺字段 / 为 `null`       | 丢弃                                                                                 |
| 昵称超长 / 非字符串          | 昵称退化为 `sessionId`，正常加入                                                     |
| 房间已有 4 人                | 第 5 个连接无法加入该房间（`joinOrCreate` 会去创建新房间）                           |
| 历史超过 50 条               | 丢弃最旧的                                                                           |
| 掉线                         | 客户端 `onLeave` 触发 → 界面回到昵称输入页并提示「与服务器断开了连接」               |
| 有人加入房间                 | 成员列表新增一项（顺序 = 加入顺序），房间里所有人实时收到                            |
| 有人离开 / 掉线              | 从成员列表移除，其余人实时收到；**聊天历史保留不动**（历史消息里的昵称也不变）       |

## 6. 服务端其它 HTTP 端点

这些不属于聊天协议，但同源部署时都在同一个域名下：

| 路径           | 方法    | 说明                                                               |
| -------------- | ------- | ------------------------------------------------------------------ |
| `/matchmake/*` | POST 等 | Colyseus 匹配接口（SDK 内部使用）                                  |
| `/api/hello`   | GET     | 示例接口，返回 `{"message":"Hello World"}`                         |
| `/hi`          | GET     | 示例 express 路由，返回一句纯文本                                  |
| `/`            | GET     | 生产环境：前端页面（`client/dist`）；开发环境：Colyseus playground |
| `/monitor`     | GET     | 仅开发环境（`@colyseus/monitor`），生产不挂载                      |

## 7. 演进规则

1. 任何字段/上限的改动都改 `shared/`（唯一真源），然后**两端一起重新构建**；
2. 新增可选字段 = 兼容变更；改字段含义、收紧上限、改消息类型名 = 不兼容变更，需升协议版本；
3. 不要复用 `chat` 消息类型传别的结构（类型名即语义）；
4. 想加「新消息事件」这类旁路通知时注意：状态同步已经承担了投递，重复用事件会导致同一条消息投递两次。
